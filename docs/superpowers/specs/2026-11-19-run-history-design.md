# InsightPilot 第二轮：运行历史与刷新恢复

日期：2026-11-19。

状态为已批准并实施。验证范围和结果见 [验收记录](../../verification.md#run-history-and-refresh-recovery--2026-11-19)。

## 1. 目标与范围

在现有分析工作流旁增加只读运行历史，让已生成的计划、完成的报告和执行记录可以在刷新后回看。继续使用现有 Next.js / React / TypeScript / Tailwind 工程和既有视觉风格。

本轮包含：

- 在当前浏览器保存运行记录，按最近更新时间展示。
- 回看问题、数据摘要、计划、Python、结果和 Trace。
- 刷新后打开最近选择的历史记录，不自动调用规划或执行接口。
- 明确显示未批准记录、连接中断记录和历史完成记录的不同含义。
- 删除单条历史、清空历史，以及存储失败时的真实提示。

本轮不包含：保存原始 CSV、云端存储、账号、跨设备同步、计划编辑、新分析操作、自动重试、沙箱重连、后台状态轮询或恢复执行。普通浏览器文件落盘仍是独立待人工验收项，不因本轮实现而改为通过。

## 2. 已选择的保存策略

方案 A：仅在当前站点、当前浏览器的本地存储中保存运行产物。方案 B（同时保存原始 CSV）已排除。

采用带版本的 typed localStorage Repository，不引入数据库或新的状态管理库。Repository 是历史记录的唯一读写入口，UI 不直接拼接存储内容。当前工作台的临时状态和现有会话级凭证机制保持独立。

本地保存的问题、文件名、报告、分组标签和 Trace 仍可能包含业务信息；“不保存原始 CSV”不等于“历史不含敏感信息”。历史入口应明确说明这一点，并说明本地存储不是加密保险箱。

不得把整个 `useWorkspace` 返回值或 `AnalysisPlan` 原对象直接序列化。只投影允许字段；历史对象不包含 API Key、credentials、approvalToken、请求头、原始 CSV、样本行或完整 DatasetProfile.rows。

## 3. 数据结构

存储键：`insightpilot.history.v1`。

顶层结构：

```ts
type RunHistoryStoreV1 = {
  version: 1
  selectedRunId: string | null
  records: AnalysisRunRecord[]
}
```

`selectedRunId` 仅用于恢复只读查看位置，不赋予执行权限。新建运行或手动选择历史时更新；删除该记录后选择最近的剩余记录，没有记录则恢复普通工作台。

每条运行记录保存：

| 字段 | 内容 |
| --- | --- |
| id | 前端生成的运行 ID，与审批凭证分离 |
| createdAt / updatedAt | ISO 时间，用于排序和标识记录时间 |
| question | 本次提交的分析问题，不保存尚未提交的输入草稿 |
| mode | demo 或 e2b |
| status | planning / needs_clarification / pending / running / completed / declined / error |
| datasetSummary | 文件名、行数、列数、缺失单元格数和重复行数；没有原始行或样本 |
| plan（可选） | planner、spec、explanation、code；显式排除 approvalToken |
| phases | 已收到的真实阶段状态快照 |
| trace | 已发生事件的消息、时间、tone 和可选 phase |
| result（可选） | 仅保存完整收流并通过校验的 AnalysisResult |
| error（可选） | 界面已使用的安全错误信息 |
| feedback（可选） | 非执行型澄清提示及可用问题建议 |

使用 Zod 验证版本、枚举、时间、结构和记录大小。完成记录必须有合法计划和结果，结果 mode 必须与记录一致，结果中的行数、缺失数、重复数必须与保存的数据摘要一致；未完成记录不得带有可发布的成功结果。现有 AnalysisResult 校验规则保持不变。历史阶段来自实际保存的事件，不因 completed 标签而补造缺失的阶段成功事件。

这不是不可篡改的审计日志：浏览器本地内容可被用户或同源脚本修改。历史报告应标注“历史结果，未重新运行”，不能暗示本次打开时重新验证过原始 CSV。

## 4. 写入时机与副作用边界

点击生成计划、通过当前输入检查后创建运行记录。输入为空、未连接所需凭证等本地阻断不创建虚假的已执行记录。

历史保存与分析执行完全分离：保存一条 planning 或 pending 记录只是保存运行说明，不创建沙箱、不上传数据，也不表示已批准。

| 现有事件 | 历史更新 |
| --- | --- |
| 开始生成计划 | planning 与数据摘要 |
| 返回澄清 | needs_clarification、feedback、Trace；没有计划凭证 |
| 计划生成成功 | pending 与无凭证的计划快照 |
| 用户拒绝 | declined；没有执行结果 |
| 用户批准 | running，随后记录真实阶段事件 |
| 干净收流并校验成功 | completed 与完整 result |
| 规划或执行失败 | error、安全消息与 Trace；没有成功 result |

记录 ID 在一次运行内保持稳定，事件更新不能制造重复历史。存储写入不放在 React state updater 的副作用中；重渲染或 Strict Mode 不应重复创建记录。已删除记录的迟到更新不能重新创建该记录。

初次加载必须先完成历史读取，再允许写入，避免以初始空状态覆盖已有历史。仅首次启动恢复查看位置；之后的历史更新或其他标签页事件不能把用户从当前工作台强行切走。

## 5. 刷新与只读恢复

历史查看与当前可执行工作台使用不同的状态。历史对象不灌回当前的 approve 路径，也不能通过填充一个假的 approvalToken 变成可执行计划。

| 历史保存状态 | 刷新后的展示与允许操作 |
| --- | --- |
| completed | 回看报告、图表、Python、Trace；允许请求导出已有产物，不重新计算 |
| pending | 显示“历史计划未恢复审批权限”；只能回看，不能点击旧批准按钮 |
| planning | 显示“当前页面未连接该规划，本地未保存最终计划”；不自动重发请求 |
| running | 显示“连接已中断，后台结果未知”；没有成功报告，不自动重跑或假称已停止 |
| declined | 保留拒绝状态与记录，不执行 |
| error | 保留失败说明与记录，不发布成功结果 |
| needs_clarification | 保留澄清说明，不伪装成分析结果 |

未连接状态是历史查看视角下的派生展示，不在读取时把原始 running 记录强制改写为失败；另一仍在线的标签页可能稍后写入真实完成结果。没有心跳、恢复连接或服务端查询时，界面不推断任务是否仍在执行。

新建分析明确返回当前工作台。由于没有保存 CSV，不提供“一键重跑历史”或把当前示例数据冒充历史源数据。重新分析需要用户准备数据、生成新计划并重新批准。刷新不会新增模型调用或消耗沙箱额度。

## 6. 页面结构

保持主工作台、主导航风格及现有卡片布局，增加一个运行历史入口和紧凑的记录列表。

- 列表显示问题或计划标题、文件名、Demo / Live 标签、状态与时间。
- 详情展示历史标识和源数据摘要，提供报告、Python、Trace 的只读视图。
- 详情不展示数据预览页签，因为历史没有保存原始行；不能混入当前工作台的数据预览。
- 只读报告使用历史的行数和列数计算数据完整度，不使用当前上传文件的 profile。
- 为避免两套报告逻辑分叉，可以局部抽取当前纯展示组件；不重写规划、审批、流解析或沙箱逻辑。
- 规划或执行进行中不允许切换到历史或删除该运行，确保用户仍能看到当前进度。刷新后的未知后台状态仍按第 5 节展示。
- 删除或清空前显示明确确认提示。删除只影响本地历史，不表示停止沙箱，不撤回已经执行的分析。

## 7. 容量、失败与一致性

- 最多保存 20 条运行记录；存储封装的序列化 UTF-8 总大小不超过 2 MiB。它们是本产品的限制，不是对所有浏览器可用配额的保证。
- 超过数量、大小或浏览器实际配额时，不自动删除旧记录，不截断报告后继续显示完整成功。当前分析仍可继续查看和导出，界面说明“未能保存本次最新历史，请删除旧记录后重试”。
- 更新保存失败时，明确历史可能只包含上一次成功保存的阶段；不能将未落盘的新结果描述成已持久化。
- 每次写入采用一次完整的单键替换；失败保留原有已保存内容。历史保存失败不能把成功的分析结果改成执行失败。
- JSON 损坏、未知版本或不合法记录显示可读警告，不能导致工作台白屏，也不能自动清空或覆盖不认识的数据。
- 存储被禁用时，分析继续工作；历史显示不可用，不假装刷新后可以恢复。
- Repository 订阅负责当前页面更新，可响应 storage 事件同步只读列表。写前重读并只更新目标运行，但不声称 localStorage 提供跨标签页事务或强一致；并发更新仍存在最后写入覆盖风险，分布式协调不在本轮范围内。

## 9. 测试与验收标准

实现时先补失败测试，再实现并回归；所有 Provider 使用 mock，不读取真实 Key。

自动测试至少覆盖：

1. 正常保存、读取、更新、选择、删除与清空；刷新后读取真实序列化记录。
2. 白名单投影排除原始 CSV、样本行、credentials、请求头和嵌套 approvalToken；不因源对象未来新增字段而自动扩大保存范围。
3. 空存储、坏 JSON、未知版本、状态/结果不一致、存储禁用、超限和配额异常。
4. 初始加载不覆盖历史；同一运行多次事件只更新一条记录；已删除记录不被迟到更新复活。
5. 历史完成结果恢复为只读，pending 无旧批准入口，planning / running 展示未连接或结果未知。
6. 历史查看、新建分析和刷新均不自动调用 plan / execute；新执行仍需当前数据与新批准。
7. 保存失败不污染当前分析结果；当前成功但历史仍为旧阶段时有清楚提示。
8. 历史报告使用历史数据摘要；不显示当前文件的样本或将其混入历史图表。
9. 同页订阅与 storage 事件更新列表，但不触发执行或抢占当前视图。
10. 原有 135 项回归测试继续通过；运行 npm test、npm run typecheck、npm run lint、npm run build，准确报告既有警告。

浏览器验收使用本地 Demo：生成并批准 → 历史出现 → 刷新后回看同一问题与数值 → 导出请求 → 删除测试记录。检查拒绝/澄清记录、没有旧批准按钮、隐私提示、移动布局和键盘操作。中断恢复若只能由离线测试验证，就单独标明，不能宣称浏览器 Live 中断验收通过。

本轮不因此重新调用真实模型或创建 E2B 沙箱。普通浏览器文件落盘、真实网络隔离、跨实例审批与并发持久化等既有边界继续保留。

## 10. 设计自检

- 保存范围与已批准的方案 A 一致，没有原始 CSV、Key 或审批凭证；问题和分析产物的潜在业务敏感性已单独说明。
- 历史查看与当前执行分离，不会使用当前示例数据冒充历史数据，也不会将旧计划还原成可批准对象。
- 未连接执行既不当作成功，也不当作已停止；读取历史不改写另一在线页面可能仍在更新的执行状态。
- 容量、配额、坏数据和多标签页限制有明确行为；没有把 localStorage 描述成事务数据库或可信审计存储。
- 第 9 节记录实施前的验收标准和 135 项测试基线。实际结果单独记录在验收文档。
